القرار الأقوى في التقرير

لا يتم دمج أي نسخة Legacy كاملة. نستمر من Current، ونستخدم Legacy C لمكونات التقارير، وLegacy B كمرجع لتنظيم الواجهة، وLegacy A لاستخراج متطلبات الأعمال فقط.

نطاق الفحص: لم تُشغّل الإضافات أو واجهات API أو حساب حضوري، ولم تُعدّل الملفات. كانت حالة Git على الفرع temp/stable-test عند 3b7c283، ومجلد legacy/ غير متتبع.

2. اكتشاف وظيفة كل نسخة

Current — الوظائف الحالية
  • التقاط سياق الجلسة ثم جلب الموظفين وحركات الحضور.
  • خط معالجة raw → index → summary.
  • متابعة يومية ومركز حركات وموظفون وإعدادات.
  • نماذج الغياب والتأخر، والطباعة وPDF وExcel.
  • واجهة RTL داخل iframe.

غير مثبت تشغيليًا في هذا الفحص. شاشة الأذونات معلوماتية، وبعض التقارير مخفية أو تجريبية، ولا يوجد اشتراك أو Backend.

Legacy A — Haduri Extra
  • اعتراض fetch وXHR وفحص تخزين الصفحة بحثًا عن دلائل جلسة.
  • تقارير وتصدير ومعاينات ونماذج.
  • Popup للإجازات مع قبول ورفض فردي وجماعي.
  • مواد دفع/ترخيص تحمل اسم Moyasar.
ينفذ endpoint لتغيير بيانات الإجازات Leaves/ApproveRejectLeave. لا يجوز نقله أو تشغيله بلا تفويض صريح ومراجعة مستقلة.
Legacy B — HSP4
  • أفضل تنظيم بنيوي: content entry وShadow DOM وshell وشاشات وstores منفصلة.
  • متابعة وموظفون ونماذج وإجازات.
  • polling كل 5 دقائق وإشعارات وشارة للطلبات.
  • عدد من مجلدات domain هو placeholder، ولذلك التنظيم لا يعني اكتمال الوظائف.
Legacy C — HSP_clean
  • Manifest وservice worker وpage hook وbroker مطابقة فعليًا لـCurrent.
  • نفس iframe والجلسة والموظفين والحركات والتقارير.
  • يمتاز بمكونات تقارير: official_notice_v2_adapter.js وofficial_notice_shared_shell.js وofficial_notice_template_v2.js.

4. الفروق البرمجية والمعمارية

Current وLegacy C

هما خط كود واحد تقريبًا، وليس قاعدتين مستقلتين. الاختلاف الأهم في ui/js/app.js ومكونات إشعارات/تقارير رسمية إضافية في Legacy C. لذلك لا يُدمج Legacy C كاملًا.

Legacy B وCurrent

content entry → bridge → Shadow DOM → shell controller → screens / stores

هذا الفصل أفضل من اعتماد Current الكبير على app.js، لكن B يعيد مخاطر الجلسة والـbroker ويضيف صلاحيات وعمليات مؤثرة.

Legacy A

الأكثر اختلافًا: منطق مركزي ضخم، Popup للإجازات، مكتبات XLSX وExcelJS وPDF وQR وMoyasar، وصلاحية تخزين غير محدودة. الدمج المباشر منه عالي الخطورة.

6. الفحص الأمني

ثلاثة مخاطر مشتركة يجب إغلاقها أولًا

  1. Bearer أو Authorization مخزن محليًا في النسخ الأربع.
  2. window.postMessage("*") وجسر رسائل عام في Current وLegacy B وC.
  3. broker يقبل URL وheaders وbody بدل عمليات ثابتة محددة.
  • Legacy A وB ينفذان اعتماد/رفض إجازات، وهي عمليات كتابة مؤثرة.
  • Legacy B يستورد خط Google عن بعد؛ يجب استخدام أصول محلية.
  • Legacy A يطلب unlimitedStorage، وLegacy B يطلب الإشعارات والمنبهات.
  • مفتاح Manifest في A هو هوية حزمة عامة، وليس سرًا، لكنه لا ينبغي نقله.
  • لا يمكن إعلان خلو المشروع من الأسرار دون فحص شامل لاحقًا للملفات والبناء والحزمة.

7. الأصل الأفضل للنسخة المطورة

Current هو الأساس — بثقة عالية

Legacy C لا يزيل المخاطر لأنه نفس الخط تقريبًا؛ Legacy B أجمل تنظيمًا لكنه غير مكتمل وأوسع صلاحيات؛ Legacy A غني وظيفيًا لكنه الأعلى مخاطرة.

  • من Legacy C: تقييم مكونات official notices والتقارير فقط.
  • من Legacy B: استلهام فصل shell/screens/stores وShadow DOM، لا نسخ الملفات.
  • من Legacy A: استخراج متطلبات الأعمال للتصفية والتصدير، لا الجلسة أو الدفع أو عمليات الاعتماد.

8. استراتيجية التطوير المقترحة

  1. تثبيت خط الأساس وحماية البيانات والجلسة: معالجة Bearer والاحتفاظ والمحو وعقد الرسائل، مع اختبارات logout و401 والرسائل السلبية.
  2. استعادة الميزات القيمة بشكل محكوم: تقارير Legacy C، وميزات الإجازات فقط إذا اعتمدت وبصلاحيات واضحة.
  3. توحيد الواجهة والتقارير والطباعة: إزالة placeholders واختبار RTL وPDF وExcel ببيانات اصطناعية.
  4. إنشاء اختبارات آلية وتشغيلية: الرسائل والتخزين والحسابات وواجهة MV3 ودورة حياة service worker.
  5. المعمارية التجارية والاشتراك: بعد تحديد الحسابات والخطط والخادم والدفع، مع entitlement خادمي.
  6. الحماية والحزمة: ZIP مطابق، فحص أسرار وتراخيص، ومراجعة المتجر على الحزمة النهائية ذاتها.

ملاحظات المراجع

تقييمي العام

التقرير قوي ومنضبط، وتوصيته الأساسية سليمة: لا فائدة من تبديل القاعدة إلى Legacy؛ القيمة الحقيقية هي استخراج الأفكار والمتطلبات مع إعادة تنفيذ الأجزاء الحساسة.

1. أتفق مع اختيار Current، لكن بشرط

اعتماد Current يجب أن يعني اعتماد وظائفه وبياناته كنقطة انطلاق، لا تثبيت معماريته الحالية. الجلسة والـbroker وحدود الرسائل تحتاج معالجة قبل إضافة الاشتراك أو توسيع الميزات.

2. خيار C هو الصحيح، مع تجنب إعادة البناء المفتوحة

أفضل صياغة له: «إعادة هيكلة موجّهة بالمخاطر فوق Current». نحافظ على الوظائف المثبتة، ونستبدل الحدود الأمنية والتراكمات تدريجيًا باختبارات. هذا يمنع تحول المشروع إلى إعادة بناء جديدة طويلة وغير قابلة للقياس.

3. الإجازات يجب فصلها إلى مستويين

  • قراءة وعرض طلبات الإجازات: يمكن دراستها لاحقًا كميزة منفصلة.
  • قبول/رفض الطلبات: عملية كتابة عالية الحساسية، وأوصي بإخراجها من الإصدار الأول حتى يتوفر تفويض صريح واختبار أمان وسجل تدقيق وتأكيد مستخدم واضح.

4. تقارير Legacy C تستحق تحققًا محدودًا

لأن C قريب جدًا من Current، يمكن مقارنة مكونات official_notice وتحديد هل هي مستخدمة فعليًا وما القيمة التي تضيفها. لا ينبغي أن تصبح هذه المقارنة مرحلة كبيرة أو تؤخر إصلاح P0.

5. Legacy B مرجع تصميم، وليس مصدر كود

فصل الشاشات والـstores مفيد، لكن اختيار iframe أو Shadow DOM ينبغي أن ينتج من احتياجات العزل والتكامل والوصولية، لا من كون B يبدو أكثر ترتيبًا.

6. تقرير المقارنة لا يثبت الجاهزية التشغيلية

الحكم NEEDS TARGETED VERIFICATION صحيح. الفحص ساكن فقط؛ لا يثبت صحة APIs أو الحسابات أو الطباعة أو دورة حياة MV3. يجب لاحقًا بناء اختبارات ببيانات اصطناعية ثم تجربة محدودة بحساب مفوض.

7. ملاحظة مهمة عن Git

مجلد legacy/ غير متتبع ويحتوي node_modules وأصولًا تاريخية وربما مواد حساسة. أوصي بعدم إدخاله في Git الحالي كاملًا. بعد استخراج ما نحتاجه، يُحفظ كأرشيف خارجي أو تُضاف قواعد استبعاد واضحة، ولا يدخل ZIP الإنتاجي إطلاقًا.

قراري المقترح الآن

وافق على الخيار C، واجعل المنتج في الإصدار الأول قراءة/تحليل/تقارير فقط. أجّل عمليات اعتماد ورفض الإجازات. نفّذ تحققًا صغيرًا من تقارير Legacy C، ثم انتقل مباشرة إلى معمارية الأمان والاشتراك بدل مزيد من تحليل النسخ.

أُعدت هذه الصفحة من تقرير المقارنة الساكن. لا تمثل نتائج اختبار تشغيلي أو موافقة نشر.
