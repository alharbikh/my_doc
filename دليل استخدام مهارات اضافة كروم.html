دليل استخدام مهارات إضافات كروم

من فكرة المشروع إلى حزمة جاهزة للرفع على Chrome Web Store

هذا الدليل صالح للاستخدام مع Codex أو Claude Code لبناء إضافة جديدة، تطوير إضافة قائمة، إصلاح تكامل مع موقع، إضافة اشتراك أو فترة تجريبية، أو تجهيز إصدار للنشر.

النتيجة النهائية المقصودة: مجلد إصدار نظيف وحزمة ZIP مطابقة له، تم اختبارهما ومراجعتهما، وجاهزان للرفع يدويًا إلى Chrome Web Store بعد موافقة صاحب المشروع.

1. المهارات وأدوارها

المهارة وقت استخدامها الناتج الأساسي
chrome-extension-orchestrator طوال المشروع تنسيق المراحل، اختيار المهارات، وضبط بوابات الموافقة
target-site-analyzer إذا كانت الإضافة تعمل على موقع محدد تقرير موثق عن الصفحات والتقنيات والجلسات واستراتيجية التكامل المسموح بها
chrome-extension-architect قبل كتابة الكود أو عند تغيير حدود رئيسية معمارية Manifest V3، الصلاحيات، الرسائل، التخزين، الأمن والخصوصية
chrome-extension-ui-designer عند وجود popup أو side panel أو options أو onboarding مخططات الواجهات، الحالات، RTL، الوصول، ونظام التصميم
chrome-extension-builder بعد اعتماد المعمارية والتصميم ملفات الإضافة والكود والاختبارات وأداة البناء
chrome-extension-tester أثناء البناء وقبل الإصدار نتائج اختبارات ووثائق أدلة وتصنيف الأعطال
extension-commercial-control عند وجود تجربة أو اشتراك أو ترخيص نموذج الصلاحيات التجارية، حالات الاشتراك، وضوابط الخادم
extension-code-protection قبل الإصدار وعند وجود منطق مميز تقليل انكشاف الكود والأسرار وحماية الحزمة ضمن سياسة المتجر
chrome-web-store-reviewer على حزمة الإصدار النهائية تحديدًا تقرير جاهزية المتجر وقرار النشر أو قائمة العوائق
agent-handoff عند تغيير الجلسة أو العميل أو النموذج تقرير تسليم موثق يمكّن الجلسة التالية من الاستمرار بأمان

لا يلزم استدعاء جميع المهارات في كل مشروع. المنسق يختار أقل مجموعة تكفي لتحقيق النتيجة.

2. إنشاء مجلد المشروع وبدء الجلسة

مشروع جديد

في PowerShell:

$Project = "$HOME\Desktop\MyChromeExtension"
New-Item -ItemType Directory -Force -Path $Project | Out-Null
Set-Location $Project
git init
codex

لاستعمال Claude Code بدل Codex:

Set-Location "$HOME\Desktop\MyChromeExtension"
claude

مشروع قائم

افتح العميل من جذر المشروع الذي يحتوي على manifest.json أو إعدادات البناء:

Set-Location "C:\path\to\extension-project"
codex

لا تشغّل جلستين تعدّلان المجلد نفسه في الوقت نفسه. يمكن تشغيل جلسات متزامنة إذا كان لكل جلسة مشروع أو worktree مستقل.

3. أمر البداية الموحد

أرسل هذا الأمر في أول جلسة:

استخدم مهارة chrome-extension-orchestrator لإدارة هذا المشروع من البداية حتى إنتاج حزمة إصدار جاهزة للمراجعة والرفع على Chrome Web Store.

ابدأ بوضع الاستقبال التفاعلي. اسألني فقط عن المعلومات التي لا تستطيع استنتاجها من ملفات المشروع. اجمع الأسئلة في دفعة قصيرة ومنظمة، ثم:
1. لخّص المتطلبات ومعايير القبول.
2. حدّد المهارات اللازمة ومسار التنفيذ في مراحل كبيرة مترابطة.
3. اذكر القرارات والمخاطر والبوابات التي تحتاج موافقتي.
4. لا تكتب الكود قبل موافقتي على نطاق المنتج والمعمارية.
5. لا تنفّذ رفعًا أو نشرًا أو دفعًا ماليًا أو تسجيل دخول نيابة عني.
6. حافظ على وثائق مشروع مختصرة، وتجنب تقسيم العمل إلى مراحل صغيرة لكل ملف.

4. أسئلة الاستقبال المطلوبة

يجب أن تغطي جلسة الاستقبال، بحسب الحاجة:

  1. اسم الإضافة ووصفها المختصر.
  2. المشكلة التي تحلها والمستخدمون المستهدفون.
  3. هل المشروع جديد أم توجد إضافة حالية؟
  4. روابط المواقع والصفحات والمسارات التي ستعمل عليها.
  5. الوظائف الأساسية والوظائف المؤجلة.
  6. البيانات التي ستقرأها أو تحفظها أو ترسلها.
  7. هل توجد مصادقة، جلسة، MFA، CAPTCHA أو حسابات حساسة؟
  8. الواجهات المطلوبة: popup، side panel، options، onboarding، صفحة كاملة أو عناصر داخل الموقع.
  9. اللغات المطلوبة، ومنها العربية وRTL.
  10. هل توجد فترة تجريبية، اشتراك، ترخيص، خطط أو إيقاف ميزات؟
  11. هل يوجد backend أو مزود دفع أو حساب مطور Chrome Web Store؟
  12. المتصفحات والإصدارات المدعومة.
  13. مستوى الاختبارات المطلوب ومعايير القبول العملية.
  14. متطلبات الخصوصية والاحتفاظ بالبيانات والدعم.

يحوّل العميل الإجابات إلى ملخص متطلبات واضح. لا يبدأ التنفيذ إلا بعد أن تقول مثلًا:

أوافق على ملخص المتطلبات والنطاق. انتقل إلى التحليل والمعمارية، ولا تبدأ البناء قبل عرض قرارات المعمارية والصلاحيات عليّ.

5. المرحلة الأولى: تحليل الموقع المستهدف

تُستخدم target-site-analyzer عندما تعتمد الإضافة على موقع محدد.

الأمر

استخدم target-site-analyzer لتحليل الموقع والصفحات المعتمدة فقط. نفّذ تحليلًا موثقًا دون بناء الإضافة ودون محاولة تجاوز تسجيل الدخول أو CAPTCHA أو الحماية.

حدّد:
- الصفحات والمسارات وحالات SPA.
- التقنيات الأمامية المؤثرة في التكامل.
- أسلوب المصادقة والجلسة دون تسجيل الأسرار.
- أسطح البيانات المسموح بها: DOM أو واجهة رسمية أو رسائل الصفحة.
- مقارنة استراتيجيات التكامل من حيث الثبات والأمان والصلاحيات.
- أقل host permissions وpermissions متوقعة.
- مخاطر تغيّر الموقع والخصوصية والأمان.
- الأدلة الناقصة والخطوات اليدوية التي يجب أن أقوم بها.

اختم بقرار: DISCOVERY COMPLETE — READY FOR ARCHITECTURE، أو اذكر العائق بدقة.

بوابة القبول

لا تنتقل للمعمارية حتى يتضح:

  • أن الاستخدام مصرح به ومتوافق مع شروط الموقع.
  • أن البيانات المطلوبة محددة ومبررة.
  • أن طريقة التكامل لا تتجاوز الحماية أو تجمع أسرارًا.
  • أن الصلاحيات المتوقعة هي الحد الأدنى.
  • أن استراتيجية DOM أو API أو page bridge مدعومة بأدلة.

6. المرحلة الثانية: المعمارية وتصميم الواجهات

يمكن تنفيذ المعمارية والتصميم في مرحلة كبيرة واحدة، مع موافقة واحدة قبل البناء.

أمر المعمارية

استخدم chrome-extension-architect وحوّل المتطلبات وتقرير الموقع المعتمد إلى معمارية Manifest V3 قابلة للتنفيذ.

حدّد:
- بنية manifest.json وأقل permissions وhost_permissions.
- مسؤوليات content scripts وservice worker وصفحات الإضافة.
- تدفقات الرسائل وعقود البيانات والتحقق منها.
- التخزين ودورة حياة البيانات والترحيلات.
- حدود الثقة والمصادقة والجلسات والأسرار.
- سياسة الأمن والخصوصية والتسجيل التشخيصي الآمن.
- الاختبارات ونقاط العزل وقابلية الصيانة.
- ADR فقط للقرارات الدائمة عالية الأثر.

لا تكتب كود الإنتاج. اعرض الحزمة المعمارية واطلب موافقتي.

أمر تصميم الواجهات

استخدم chrome-extension-ui-designer لتصميم الواجهات المعتمدة في المتطلبات.

قدّم:
- اختيار السطح المناسب: popup أو side panel أو options أو onboarding.
- مخططات واضحة لكل شاشة.
- حالات التحميل والنجاح والفراغ والخطأ وانتهاء الجلسة وعدم الصلاحية.
- نظام ألوان وخطوط ومسافات ومكونات.
- دعم العربية وRTL والوصول ولوحة المفاتيح.
- شاشات التجربة والاشتراك إذا كانت ضمن النطاق.
- مواصفات تنفيذية يستطيع builder تحويلها مباشرة إلى كود.

لا تنفّذ الواجهات بعد. اعرض التصميم واطلب موافقتي.

بوابة التصميم

يجب اعتماد:

  • هدف واحد واضح للإضافة.
  • الصلاحيات وأسباب كل صلاحية.
  • تدفقات الرسائل والتخزين والجلسة.
  • الواجهات وحالاتها الأساسية.
  • معايير القبول والاختبارات.
  • الحدود التجارية والخادم إن وجدت.

أمر الموافقة:

أوافق على المعمارية والتصميم والصلاحيات الموضحة. ابدأ البناء ضمن هذا النطاق فقط، وتوقف إذا احتجت صلاحية أو خدمة أو حد ثقة جديدًا.

7. المرحلة الثالثة: بناء الإضافة وكتابة ملفاتها

نعم، chrome-extension-builder يكتب الملفات والأوامر البرمجية، ومنها:

  • manifest.json وفق Manifest V3.
  • content scripts وservice worker.
  • popup وside panel وoptions وonboarding.
  • HTML وCSS وJavaScript أو TypeScript وإطار الواجهة المعتمد.
  • الرسائل والتخزين والترحيلات.
  • adapters خاصة بالموقع.
  • الاختبارات وأداة البناء.
  • ملفات التوثيق والإصدار الضرورية.

أمر البناء

استخدم chrome-extension-builder لتنفيذ المعمارية والتصميم المعتمدين كشرائح رأسية متماسكة، وليس كمرحلة منفصلة لكل ملف.

متطلبات التنفيذ:
1. أنشئ ملفات المشروع وكود Manifest V3 الفعلي.
2. التزم بأقل الصلاحيات، ولا تضف remote hosted code.
3. لا تخزن كلمات مرور أو cookies أو tokens أو بيانات حساسة في السجلات.
4. طبّق عقود رسائل محققة وحدودًا واضحة بين المكونات.
5. أضف اختبارات مركزة مع كل قدرة رئيسية.
6. شغّل التنسيق والفحص والاختبارات بعد كل شريحة كبيرة.
7. لا تغيّر المعمارية أو توسع النطاق دون موافقتي.
8. لا تنفذ git commit أو push إلا إذا أذنت بذلك صراحة.
9. عند إكمال القدرة، اعرض الملفات المتغيرة والاختبارات والقيود المتبقية.

بنية نموذجية للمشروع

project/
├── src/
│   ├── background/
│   ├── content/
│   ├── popup/
│   ├── sidepanel/
│   ├── options/
│   ├── shared/
│   └── site-adapters/
├── public/
│   ├── manifest.json
│   └── icons/
├── tests/
├── docs/
├── package.json
└── build configuration

البنية الفعلية تتبع المعمارية والأداة المختارة، ولا يجب إنشاء مجلدات غير مستخدمة.

8. المرحلة التجارية: التجربة والاشتراك والترخيص

تُستخدم extension-commercial-control فقط إذا كان المشروع تجاريًا.

المبدأ الحاسم

لا يمكن الاعتماد على واجهة الإضافة وحدها لحماية الميزات المدفوعة. يستطيع المستخدم تعديل الكود المحلي. يجب أن تكون الصلاحيات والميزات الحساسة قابلة للتحقق من خادم موثوق عند الحاجة.

الأمر

استخدم extension-commercial-control لتصميم وتنفيذ نظام التجربة والاشتراك ضمن المعمارية المعتمدة.

غطِّ:
- الحساب والهوية والربط الآمن.
- بداية التجربة ونهايتها ومنع إعادة التجربة غير المصرح بها.
- الخطط والميزات entitlements بدل الاعتماد على زر مخفي محليًا.
- التجديد والإلغاء والتعليق وفشل الدفع وفترة السماح.
- حدود الأجهزة والجلسات والوضع غير المتصل.
- webhooks وتوقيعها ومنع إعادة الإرسال.
- الإيقاف الجزئي أو الكامل بطريقة واضحة وآمنة للمستخدم.
- اختبارات العبث والانقطاع وانتهاء الاشتراك.
- الإفصاحات والخصوصية وإدارة الحساب.

أوقف التنفيذ عند أي قرار قانوني أو مزود دفع أو تغيير في البيانات يحتاج موافقتي.

9. الاختبار والتحقق العملي

استخدم chrome-extension-tester بعد كل قدرة كبيرة، ثم مرة أخيرة على حزمة الإصدار.

الاختبارات المطلوبة بحسب المشروع

  • فحص صحة manifest.json.
  • unit tests للمنطق والعقود.
  • اختبارات رسائل بين المكونات.
  • اختبارات التخزين والترحيل.
  • تحميل الإضافة Unpacked في Chrome.
  • اختبار الصفحات والمسارات المستهدفة.
  • اختبار تسجيل الدخول وانتهاء الجلسة دون كشف بيانات حساسة.
  • اختبار بدء وتوقف service worker.
  • اختبار الصلاحيات الاختيارية والمرفوضة.
  • اختبار popup أو side panel أو options وحالات الخطأ.
  • اختبار العربية وRTL والوصول.
  • اختبار إعادة تشغيل المتصفح وتحديث الإضافة.
  • اختبار انقطاع الشبكة والموقع وتغير الاستجابة.
  • اختبار التجربة والاشتراك والعبث إذا كان المشروع تجاريًا.

أمر الاختبار

استخدم chrome-extension-tester للتحقق من الإضافة دون إصلاح الأعطال أثناء مرحلة التشخيص.

1. ثبّت هوية النسخة وcommit وحزمة الاختبار والمتصفح والموقع.
2. شغّل الاختبارات الآلية والمتصفح والسيناريوهات الواقعية المناسبة.
3. اجمع أدلة منقحة لا تحتوي على أسرار أو بيانات شخصية.
4. صنّف كل فشل إلى كود الإضافة أو الموقع أو الجلسة أو الصلاحيات أو البيئة.
5. اذكر أقل تجربة تالية تفصل بين الأسباب عند عدم اليقين.
6. قدّم تقرير PASS/FAIL ولا تدّع نجاح اختبار لم يُنفذ.

إذا ظهرت أعطال، يُعاد الإصلاح إلى chrome-extension-builder ضمن نطاق معتمد، ثم يعاد الاختبار المميز واختبارات الانحدار.

10. حماية الكود والأسرار

استخدم extension-code-protection قبل إنشاء حزمة الإصدار.

حقائق يجب اعتمادها

  • لا يمكن منع المستخدم تمامًا من قراءة كود الإضافة المثبتة.
  • لا تضع مفاتيح API سرية أو أسرار خادم داخل الإضافة.
  • انقل المنطق السري والقيم التجارية الحساسة إلى backend.
  • استخدم minification متوافقًا مع سياسة المتجر، ولا تستخدم obfuscation يخفي وظيفة الكود عن المراجعين.
  • احذف source maps وملفات التطوير والاختبارات والأسرار من حزمة الإصدار.

الأمر

استخدم extension-code-protection لمراجعة مشروع الإضافة وحزمة الإصدار.

أنشئ جردًا لما يمكن للمستخدم رؤيته، وابحث عن الأسرار والمنطق المميز وsource maps وملفات التطوير والتبعيات والتراخيص. اقترح أو نفّذ الحماية المسموح بها فقط: نقل المنطق الحساس للخادم، minification متوافق، تنظيف الحزمة، منع تسرب الأسرار، وضبط provenance للبناء.

لا تستخدم obfuscation محظورًا، واذكر بوضوح المخاطر المتبقية التي لا يمكن إزالتها من كود العميل.

11. إنشاء حزمة الإصدار

استخدم أوامر المشروع الفعلية. في مشروع Node نموذجي قد تكون:

npm ci
npm run lint
npm test
npm run build

يجب أن ينتج البناء مجلدًا مثل:

dist\

تحقق أن manifest.json موجود مباشرة في جذر dist:

Test-Path ".\dist\manifest.json"

اعرض الملفات قبل الضغط:

Get-ChildItem ".\dist" -Recurse | Select-Object FullName, Length

أنشئ ZIP بحيث يكون manifest.json في جذر الملف المضغوط، لا داخل مجلد dist إضافي:

$Version = "1.0.0"
$Release = ".\release\my-extension-$Version.zip"
New-Item -ItemType Directory -Force ".\release" | Out-Null
Compress-Archive -Path ".\dist\*" -DestinationPath $Release -Force
Get-FileHash $Release -Algorithm SHA256

لا تنشئ الحزمة من مجلد المصدر. استخدم مخرجات الإنتاج النظيفة فقط.

12. مراجعة Chrome Web Store النهائية

يجب تشغيل chrome-web-store-reviewer على ملف ZIP النهائي نفسه، لأن مراجعة المصدر وحده لا تكفي.

الأمر

استخدم chrome-web-store-reviewer لمراجعة ملف ZIP النهائي المحدد، وليس المصدر فقط، وفق السياسات الحالية وقت المراجعة.

تحقق من:
- Manifest V3 والغرض الواحد الواضح.
- أقل permissions وhost_permissions وتبريرها.
- عدم وجود remote hosted code أو obfuscation محظور.
- قابلية قراءة الكود بعد minification المقبول.
- التعامل مع بيانات المستخدم وسياسة الخصوصية والإفصاحات.
- تسجيل الدخول والمدفوعات والاشتراكات والتجربة.
- جودة الوظائف والواجهات والوصول.
- نصوص وصور صفحة المتجر واتساقها مع السلوك.
- بيانات وصول المراجع إن كانت مطلوبة دون كشف أسرار في المستودع.
- نظافة ZIP وعدم وجود source maps أو اختبارات أو أسرار أو ملفات غير مستخدمة.
- مخاطر التحديث من الإصدار السابق إن وجدت.

أصدر أحد الحكمين:
1. READY FOR SUBMISSION — EXTERNAL AUTHORIZATION REQUIRED
2. NOT READY، مع عوائق مرتبة حسب الشدة وطريقة التحقق بعد الإصلاح.

لا ترفع الحزمة ولا تنشرها.

حزمة التسليم المطلوبة

يجب أن تحتوي نتيجة المشروع النهائية على:

  • ملف ZIP النهائي.
  • SHA-256 للحزمة.
  • رقم الإصدار وcommit أو tag المرجعي.
  • تقرير الاختبارات.
  • تقرير مراجعة المتجر.
  • سياسة الخصوصية عند الحاجة.
  • وصف المتجر ولقطات الشاشة والأيقونات المطلوبة.
  • تعليمات المختبر أو المراجع عند الحاجة.
  • قائمة بالمخاطر أو الأعمال المؤجلة.

13. الرفع والنشر

الرفع إلى Chrome Web Store إجراء خارجي منفصل، ولا ينفذه العميل تلقائيًا دون إذن صريح.

بعد الحكم:

READY FOR SUBMISSION — EXTERNAL AUTHORIZATION REQUIRED

يقوم صاحب المشروع يدويًا بما يلي:

  1. تسجيل الدخول إلى حساب مطور Chrome Web Store.
  2. رفع ملف ZIP الذي تمت مراجعته بالضبط.
  3. إدخال بيانات صفحة المتجر والخصوصية واستخدام البيانات.
  4. إضافة صور وأيقونات الإصدار.
  5. توفير تعليمات المراجع أو حساب اختبار محدود عند الحاجة.
  6. مراجعة الإفصاحات والأسعار والاشتراك.
  7. إرسال النسخة للمراجعة أو جدولة النشر.

لا تُعد الإضافة منشورة لمجرد أن ZIP جاهز؛ الجاهزية والرفع والموافقة والنشر حالات منفصلة.

14. نقاط التحقق وإدارة Git

عند نهاية كل مرحلة كبيرة، اطلب تقريرًا يتضمن:

  • الهدف والنتيجة والحكم.
  • branch وHEAD قبل وبعد العمل.
  • الملفات التي تغيرت.
  • الاختبارات التي نُفذت فعلًا ونتائجها.
  • الصلاحيات والبيانات والحدود التي تغيرت أو بقيت.
  • ما لم يُنفذ.
  • العوائق والمخاطر.
  • المرحلة التالية المسموح بها فقط.

قبل commit:

راجع diff والملفات المرشحة للـcommit. تأكد من عدم وجود أسرار أو بيانات شخصية أو ملفات بناء أو تغييرات خارج النطاق. لا تنفذ commit حتى تعرض النتيجة وتحصل على موافقتي.

بعد الموافقة فقط:

أنشئ commit واحدًا مركزًا لهذه المرحلة بالملفات المعتمدة فقط، ثم اعرض hash والحالة النهائية. لا تنفذ push.

يحتاج push أو إنشاء PR أو رفع المتجر إلى موافقة مستقلة.

15. نقل العمل بين Codex وClaude

قبل إغلاق جلسة أو الانتقال إلى عميل آخر:

استخدم agent-handoff وأنشئ تقرير تسليم موثقًا للمشروع الحالي إلى Codex/Claude. تحقق من branch وHEAD وgit status والملفات المعدلة والاختبارات والقرارات والعوائق والخطوة التالية. لا تعدّل الكود ولا تنفذ commit أو push.

في الجلسة الجديدة:

اقرأ تقرير التسليم والوثائق الأساسية، ثم تحقّق بنفسك من branch وHEAD وgit status قبل أي تعديل. اذكر ما تأكدت منه وأي اختلاف. لا تستأنف التنفيذ حتى يصبح checkpoint موثوقًا.

16. الأمر الشامل لمشروع جديد

يمكن استعمال هذا النص كبداية سريعة:

استخدم chrome-extension-orchestrator لإدارة إنشاء إضافة كروم Manifest V3 كاملة في هذا المجلد حتى إنتاج ZIP جاهز لمراجعة Chrome Web Store.

اعمل بالمراحل الكبيرة التالية:
1. استقبال تفاعلي وملخص متطلبات ومعايير قبول.
2. تحليل الموقع باستخدام target-site-analyzer إذا كانت الإضافة مرتبطة بموقع.
3. معمارية وصلاحيات باستخدام chrome-extension-architect، وتصميم واجهات باستخدام chrome-extension-ui-designer.
4. بناء الملفات والكود والاختبارات باستخدام chrome-extension-builder.
5. ضوابط تجارية باستخدام extension-commercial-control إذا كان الاشتراك أو التجربة ضمن النطاق.
6. اختبار آلي وتشغيلي باستخدام chrome-extension-tester.
7. حماية أسرار وكود وتنظيف حزمة باستخدام extension-code-protection.
8. بناء ZIP إنتاجي نهائي ومراجعته باستخدام chrome-web-store-reviewer.

قواعد العمل:
- اسألني أولًا ولا تفترض قرارات المنتج غير الموجودة.
- لا تبدأ البناء قبل موافقتي على المعمارية والصلاحيات.
- لا تتجاوز مصادقة الموقع أو شروطه ولا تطلب كلمات مرور أو tokens.
- استخدم أقل صلاحيات وأقل بيانات لازمة.
- لا تستخدم remote hosted code أو obfuscation مخالفًا.
- لا تقسّم المشروع إلى مرحلة لكل ملف؛ اجمع العمل في نتائج كبيرة قابلة للاختبار.
- لا تدّع نجاح اختبار لم تنفذه.
- لا تنفذ commit أو push أو رفعًا أو نشرًا أو دفعًا ماليًا دون موافقة منفصلة.
- توقف عند أي تغيير جديد في الثقة أو الصلاحيات أو التخزين أو backend أو الاشتراك للحصول على موافقتي.

ابدأ الآن بأسئلة الاستقبال فقط.
