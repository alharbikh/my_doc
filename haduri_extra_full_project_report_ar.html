تقرير تحليلي شامل لمشروع "حضوري اكسترا" (Haduri Extra)

تاريخ الإعداد: 2026-07-25<br>نوع الوثيقة: تقرير تحليل تقني شامل (بدون أي تعديل على سلوك الكود)<br>المصدر: قراءة مباشرة لملفات المشروع + تدقيق الوثائق التدقيقية الموجودة مسبقًا في مجلد docs/

1. نظرة عامة على المشروع

حضوري اكسترا إضافة متصفح Chrome (Manifest V3) تعمل فوق منصة الحضور والانصراف الحكومية الرسمية التابعة لوزارة التعليم السعودية على النطاق:

https://hather-ui.moe.gov.sa/*

الاسم الظاهر في manifest.json: "حضوري اكسترا - Smart Report"، والوصف الرسمي المسجّل هو:

"نظام التقارير الذكي لإدارة الحضور والانصراف. حسابات دقيقة، تصدير Excel/PDF، وتفعيل فوري. مسجل بالملكية الفكرية (26-12-64959711)."

الإصدار الحالي: 9.0.0.

الإضافة لا تُنشئ نظام حضور مستقل، بل تُضيف طبقة تقارير وتحليل واحتساب ذكية فوق بيانات الحضور والانصراف والإجازات التي يوفرها موقع "حاضري" الحكومي، عبر:

  • اعتراض طلبات الشبكة (fetch/XHR) لصفحة الموقع نفسها لالتقاط التوكن وبيانات الحساب دون تسجيل دخول منفصل،
  • إعادة استخدام نفس السياق المصادق عليه (Authorization headers) لإعادة طلب البيانات بشكل شامل (كل الموظفين، فترات زمنية أطول)،
  • حَقن واجهة مستخدم كاملة (أزرار، نوافذ منبثقة، جداول، تقارير) مباشرة داخل صفحة الموقع نفسه،
  • تشغيل نظام اشتراك/ترخيص مدفوع مستقل عبر بوابة دفع خارجية (Moyasar) وخدمة توثيق ترخيص خارجية (Supabase).

2. الخدمات التي يقدمها المشروع

بحسب الأزرار والوظائف الفعلية داخل content.js، تقدّم الإضافة:

  1. تقرير الحضور اليومي الشامل — يعرض لكل موظف: حالة الحضور، وقت الحضور، موقع البصمة، التأخير، وقت الانصراف، موقع الانصراف، الانصراف المبكر، والملاحظات (إجازة/استئذان/غياب).
  2. فلترة تفاعلية فورية لنفس اليوم حسب: الكل / الحاضرون / الغائبون / المتأخرون / المنصرفون مبكرًا / الإجازات والاستئذانات، عبر بطاقات إحصائية قابلة للنقر.
  3. تقارير شهرية (فردية وجماعية): تقرير شهري مفصّل لموظف واحد، تقرير الغياب الشهري، تقرير التأخير الشهري، تقرير الانصراف المبكر الشهري، تقرير الإجازات الشهري.
  4. تقارير سنوية (فردية وجماعية): التقرير السنوي الشامل، تقرير التأخير السنوي، تقرير الانصراف المبكر السنوي، تقرير غياب الموظف السنوي، وتقرير سنوي جماعي متعدد الموظفين.
  5. تقرير المساءلة/المخالفين (Violators / Accountability) — قائمة موظفين يمكن اختيارهم لإنشاء إشعار مساءلة رسمي (توجد صفحة معاينة مستقلة preview_accountability.html).
  6. تصدير التقارير بصيغ متعددة: Excel (.xls/.xlsx)، PDF، وJSON خام.
  7. تنزيل قالب بيانات موظفين (قالب_بيانات_الموظفين.xlsx) لرفع/تحديث بيانات الموظفين يدويًا.
  8. جلب شامل بين تاريخين يتجاوز حدود صفحة الموقع الأصلية (حتى 62 يومًا/شهرين في الطلب الواحد).
  9. نظام اشتراك وترخيص مدفوع بخطط ربع سنوية / نصف سنوية / سنوية، مع دفع فوري وتفعيل تلقائي واسترجاع ترخيص سابق.
  10. بوابة شروط استخدام إلزامية يجب قبولها قبل استخدام أي ميزة.

3. التقنيات والمكتبات المستخدمة

البنية التقنية العامة

  • Chrome Extension Manifest V3 بدون أي framework (لا React / لا Vue / لا Angular). كل الواجهات تُبنى بـ Vanilla JavaScript وحقن HTML/CSS مباشر في DOM.
  • لا يوجد نظام بناء (build system) ظاهر (لا package.json تشغيلي، لا bundler كـ Webpack/Vite) — الملفات تُشحن كما هي.
  • content.js ملف ضخم واحد (~884 كيلوبايت، أكثر من 21,000 سطر) يمثل قلب التطبيق التشغيلي بالكامل تقريبًا (واجهة، منطق أعمال، تخزين، دفع، ترخيص).

4. البنية التشغيلية (Architecture)

نقاط الدخول الفعلية في manifest.json

"content_scripts": [
  { "js": ["injected/interceptor.js"], "world": "MAIN", "run_at": "document_start" },
  { "js": ["developer/dev_internal_track_resolver.js", "xlsx.full.min.js",
           "pdf-generator.js", "moyasar.js", "content.js"], "run_at": "document_start" }
]
  • لا يوجد Background/Service Worker فعّال، ولا default_popup، ولا options_page مفعّلة رغم وجود ملفات popup.html/popup.js (تُعتبر ملفات قديمة/خاملة غير موصولة بالمانفست الحالي).
  • الصلاحيات المطلوبة (permissions) هي storage وunlimitedStorage فقط — لا صلاحيات شبكة واسعة (host_permissions واسعة)، ولا tabs، ولا scripting صريحة، وهو مستوى صلاحيات محدود نسبيًا لإضافة بهذا الحجم.

تسلسل الإقلاع (Boot Flow)

  1. عند فتح صفحة hather-ui.moe.gov.sa، يعمل injected/interceptor.js في عالم الصفحة (MAIN world) منذ document_start.
  2. هذا الملف "يلف" (wrap) دوال fetch وواجهات XMLHttpRequest (open/send/setRequestHeader)، ويفحص دوريًا localStorage/sessionStorage بحثًا عن كائنات مستخدم/حساب وتوكنات.
  3. يبث النتائج عبر window.postMessage برسائل مثل HADURI_API_CAPTURED وHADURI_DEPARTMENT_DATA_CAPTURED.
  4. بالتوازي، تُحمَّل الملفات developer/dev_internal_track_resolver.js ثم xlsx.full.min.js وpdf-generator.js وmoyasar.js ثم content.js في "عالم" الإضافة المعزول.
  5. content.js يستمع لرسائل الالتقاط، يخزّن معلومات نقطة النهاية الموثّقة (haduri_api_transaction_endpoint)، ثم يستخدمها لاحقًا لإعادة طلب البيانات بشكل شامل لكل الموظفين/كل الفترات.
  6. إن لم يلتقط أي طلب مناسب، يحاول content.js بناء طلب افتراضي بقراءة التوكن مباشرة من تخزين الصفحة (token/access_token/authToken) مع CSRF token من <meta name="csrf-token">.
  7. تُحقن أزرار وقوائم الإضافة داخل رأس صفحة الموقع نفسها عبر startButtonMonitoring() بشكل مستمر (لأن الموقع تطبيق Angular أحادي الصفحة SPA، فالرأس قد يُعاد رسمه).

نموذج المصادقة (Auth Model)

  • لا يوجد نظام تسجيل دخول خاص بالإضافة إطلاقًا. الإضافة "تستعير" جلسة تسجيل الدخول الحالية للمستخدم على موقع حاضري نفسه (Authorization header الملتقَط، أو التوكن المخزَّن في localStorage/sessionStorage للموقع).
  • هذا يعني أن أمان الوصول للبيانات الحكومية يعتمد كليًا على أمان جلسة الموقع الأصلي، لا على أي طبقة مصادقة إضافية من الإضافة.

5. آلية اعتبار الموظف "حاضرًا"

الاحتساب مبني على حقلين أساسيين تُشتق منهما كل الحالات: hadir (وقت الحضور) وinsiraf (وقت الانصراف)، إضافة إلى حقل ملاحظات ejazat.

مصدر القيم الخام

  • الحقول القادمة من واجهة Reports/GetWorkReportByInterval وواجهات المعاملات (Transaction/GetAllTransaction) هي: CheckInDate, CheckOutDate, TransactionTypeID, Status, ResultStatus, IsAbsence, IsLeave.
  • تنظيف أولي: يتم استبعاد القيم الوهمية/الفارغة مثل 00:00 و0001-01-01 قبل أي احتساب.
  • حضور = أقدم وقت CheckInDate صالح لليوم (وليس كل الحركات بالتساوي).
  • انصراف = أحدث وقت CheckOutDate صالح لليوم.
  • TransactionTypeID = 0 ⇐ حضور، TransactionTypeID = 1 ⇐ انصراف، 2/3 ⇐ حالات أخرى غير موحّدة دلاليًا في الكود الحالي (لا يوجد جدول تعريف رسمي كامل لهما).

منطق تصنيف اليوم (present / absent / leave)

يظهر بوضوح في منطق فلترة "الغائبين" داخل exportHaduriExtraPDF وما يقابله في عرض الجدول:

  1. إن وُجد وقت حضور فعلي (hadir صالح أو _checkInDate) ⇒ حاضر، بصرف النظر عن أي ملاحظة أخرى.
  2. إن لم يوجد حضور فعلي:
  • إن لم توجد ملاحظة (ejazat) على الإطلاق، أو كانت الملاحظة حرفيًا "غائب"/"غياب" ⇒ غياب حقيقي.
  • إن احتوت الملاحظة على كلمات مفتاحية مثل: إجازة, اجازة, استئذان, استيذان, مأمورية, مهمة (وفي مسارات أخرى أيضًا: عيد, عطلة, رسمية, وطنية, مطولة, اعتيادية, وأحيانًا راحة, مرضي, طبية) ⇒ لا يُحتسب غيابًا، بل يُصنَّف ضمن الإجازات/الاستئذانات.
  1. الحالة الافتراضية للحالة اليومية المدمجة تبدأ كـ"غياب" (assumed absent) حتى تُثبت حركة صالحة أو استثناء (إجازة) عكس ذلك.

هذا يعني أن الحضور مبني على وجود حركة زمنية فعلية فقط، بينما الغياب استنتاجي بالحذف (لا يوجد حضور ولا يوجد استثناء نصّي يبرره)، وليس بناءً على حقل Status/IsAbsence وحده — رغم أن هذه الحقول تُقرأ وتُستخدم أحيانًا كإشارة داعمة عندما لا توجد حركة حضور/انصراف صالحة إطلاقًا لليوم.

6. التعامل مع حركات الحضور المكرّرة (Duplicate Movements)

التعامل مع التكرار يحدث على طبقتين منفصلتين:

الطبقة الأولى — تبسيط الحركات الخام لليوم الواحد

عند معالجة قائمة حركات خام متعددة لنفس اليوم لنفس الموظف (قد يبصم الموظف عدة مرات دخولًا/خروجًا)، لا تُحتفظ كل حركة كسجل منفصل، بل:

  • يُؤخذ أقدم وقت حضور صالح فقط (hadir)،
  • يُؤخذ أحدث وقت انصراف صالح فقط (insiraf)،
  • بقية الحركات الوسيطة تُهمَل عمليًا من حيث القيمة الظاهرة في التقرير (رغم أنها قد تبقى في المصفوفة الخام قبل الدمج).

الطبقة الثانية — دمج نتائج عدة عمليات جلب (fetch) عبر Map بمفتاح مركّب

عند حفظ الحركات في haduri_data، يُستخدم مفتاح دمج هو ${id}_${name} (معرّف الموظف + الاسم) داخل Map:

const movementMap = new Map();
existingMovements.forEach(m => { /* إضافة الموجود مسبقًا */ });
normalized.forEach(m => {
  if (!movementMap.has(key)) {
    movementMap.set(key, { ...m }); // حركة جديدة تمامًا
  } else {
    // دمج "الأول يفوز" لكل حقل فارغ فقط:
    if (m.hadir && !existing.hadir) existing.hadir = m.hadir;
    if (m.insiraf && !existing.insiraf) existing.insiraf = m.insiraf;
    if (m.school && !existing.school) existing.school = m.school;
    if (m.schoolOut && !existing.schoolOut) existing.schoolOut = m.schoolOut;
    // ... نفس المنطق للملاحظات ونوع الحركة
  }
});

النتيجة العملية: إذا امتلك السجل الموجود مسبقًا قيمة hadir بالفعل، فإن أي حركة جديدة تحمل قيمة hadir مختلفة لن تستبدلها (سياسة "أول قيمة تفوز" وليس "آخر/أحدث قيمة تفوز" في طبقة الدمج هذه). هذا يختلف عن الطبقة الأولى التي تعتمد فعليًا الأقدم/الأحدث زمنيًا وقت البناء الأول للسجل اليومي.

ملاحظة تدقيقية مهمة: مفتاح الدمج ${id}_${name} لا يتضمن التاريخ، ما يعني أن منطق الدمج هذا مصمَّم لسياق "يوم واحد محدد مسبقًا" (لا لعدة أيام مختلفة في نفس المصفوفة)، وإلا فسيحدث تداخل بين أيام مختلفة لنفس الموظف. هذا يتوافق مع كون haduri_data مرتبطًا عادة بتاريخ محدد يُختار من واجهة التقرير اليومي.
  • توجد أيضًا آلية Set (seenIds) في مسار منفصل لكشط قوائم الموظفين من صفحات متعددة (Pagination) لمنع تكرار نفس الموظف عبر الصفحات.
  • تعليقات صريحة في الكود تُظهر وعيًا تاريخيًا بمشكلة التكرار: مثل حذف دالة مكررة (parseTimeToMinutes) والإبقاء على نسخة واحدة فقط، وإزالة زر تقرير مكرر، وإزالة عنوان مكرر عند دمج تقارير Excel متعددة لموظفين في ملف واحد (فواصل صفحات page-break).

7. احتساب التأخير والانصراف المبكر

التأخير (takheer)

  1. تنظيف القيم الوهمية من CheckInDate.
  2. اختيار أقدم وقت حضور صالح لليوم.
  3. قراءة وقت بداية الدوام الرسمي من حقل الإدخال الحي في الواجهة #haduri-start-time (يُعبَّأ مسبقًا من الإعداد المخزَّن haduri_work_start، القيمة الافتراضية الظاهرة في الكود قريبة من بداية الدوام الرسمي).
  4. تحويل الوقتين (الحضور الفعلي ووقت البداية الرسمي) إلى دقائق.
  5. إن كان وقت الحضور الفعلي متأخرًا عن وقت البداية ⇒ الفرق الموجب = دقائق التأخير.
  6. تنسيق النتيجة كـ HH:MM وتخزينها في حقل takheer.

الانصراف المبكر (mobakker)

منطق مطابق تمامًا لكن بالاتجاه المعاكس:

  1. أحدث وقت انصراف صالح لليوم مقابل وقت نهاية الدوام الرسمي المقروء من #haduri-end-time (المرتبط بالإعداد haduri_work_end).
  2. إن كان الانصراف الفعلي أبكر من وقت النهاية الرسمي ⇒ الفرق = دقائق الانصراف المبكر، تُنسَّق HH:MM وتُخزَّن في mobakker.

حالة "الاستئذان" (تأخير/انصراف مبكر مبرَّر)

  • عندما يكون التأخير أو الانصراف المبكر مبرَّرًا باستئذان رسمي، تتم إضافة إشارة سالبة نصية أمام القيمة، مثل: emp.mobakker = "-" + emp.mobakker; (والمثيل ذاته لـtakheer في مسارات أخرى). هذه القيم السالبة تُستثنى بعد ذلك من بعض الإجماليات الإحصائية العامة (لأنها "مبرَّرة" وليست مخالفة فعلية).

حد التهاون (Threshold) — غير مفعَّل عمليًا

  • يوجد إعداد مخزَّن باسم haduri_late_threshold_minutes يُحمَّل إلى حالة التشغيل، لكن لم يُعثر على أي فرع حسابي فعلي في مسارات التأخير المدقَّقة يستخدم هذا الحد (أي لا توجد "فترة سماح" مطبَّقة فعليًا في المعادلة رغم وجود الإعداد الجاهز له).

8. التقارير التي ينتجها المشروع وهيكلها العام

8.1 القائمة الكاملة للتقارير

8.2 الهيكل العام لكل تقرير (تصميم موحّد)

كل تقرير — سواء عُرض داخل نافذة منبثقة في الصفحة أو صُدِّر — يتبع نمطًا بصريًا موحّدًا:

  1. رأس التقرير (Header): شعار المؤسسة/الوزارة (images/logo.png أو ما يعادله)، اسم جهة العمل (org) واسم المدير المسؤول (manager) — تُقرأ من بيانات التفعيل النشطة، أو تُستبدل بقيم افتراضية عامة ("وزارة التعليم" / "مدير الإدارة") إن لم يكن هناك اشتراك فعّال.
  2. عنوان التقرير ديناميكي حسب النوع/الفلتر المختار (مثال: "تقرير التأخر"، "تقرير الغياب الشهري - يناير 2026").
  3. بطاقات إحصائية ملخّصة أعلى الجدول (إجمالي، حاضرون، غائبون، متأخرون، منصرفون مبكرًا، إجازات) — قابلة للنقر للفلترة الفورية.
  4. جدول تفصيلي بأعمدة تختلف حسب نوع التقرير، لكنها غالبًا تشمل: الرقم التسلسلي، اسم الموظف (موثّق/مُحقَّق من قائمة رئيسية verified_employees_map)، الرقم الوظيفي، وقت/موقع الحضور، وقت/موقع الانصراف، التأخير، الانصراف المبكر، الملاحظات.
  5. دعم اتجاه RTL كامل وخط Tajawal موحَّد، مع تلميحات Excel صريحة لليمين-إلى-اليسار (x:DisplayRightToLeld / RTL workbook views) في ملفات التصدير.
  6. تذييل/بيانات رسمية (في تقارير PDF تحديدًا) قد تشمل رمز QR (عبر qrcode.min.js) وبيانات تنظيمية.
  7. فواصل صفحات (page-break) عند دمج عدة تقارير فردية (مثل تقارير شهرية لعدة موظفين) في ملف تصدير واحد.

8.3 آليات التصدير الفعلية (مهم تقنيًا)

يستخدم المشروع أسلوبين مختلفين تمامًا للتصدير حسب نوع التقرير:

  • HTML متنكّر بصيغة Excel (.xls) — الأسلوب الأساسي في التقرير اليومي، التقرير الشامل بين تاريخين، والتقارير الشهرية/السنوية. يتم توليد جدول HTML كامل بأنماط داخلية (inline styles) + توجيهات Excel الخاصة (xmlns:x="urn:schemas-microsoft-com:office:excel")، ثم تغليفه في Blob وتنزيله بامتداد .xls. هذه ليست ملفات Excel حقيقية (binary workbook)، بل ملفات HTML يفتحها Excel بنجاح.
  • ملفات .xlsx حقيقية عبر SheetJS — تُستخدم فقط في مسار "قالب بيانات الموظفين" وبعض مسارات popup القديمة، عبر XLSX.utils.json_to_sheet → XLSX.utils.book_new → XLSX.write(..., {bookType:"xlsx", type:"array"}) ثم Blob + URL.createObjectURL + رابط تنزيل مؤقّت (وليس XLSX.writeFile مباشرة، لأن الكود يذكر صراحة أنها غير موثوقة داخل content script).
  • PDF يُولَّد عبر مكتبة داخلية مخصّصة HaduriPDFGenerator (pdf-generator.js) بتصميم بصري خاص (ألوان، شعارات، تخطيط) وليس عبر مكتبة PDF عامة مثل jsPDF/html2pdf.

9. مستوى الحماية وكيف تتم الحماية

9.1 لا يوجد تشفير محلي فعلي

تم فحص الكود بحثًا عن crypto/encrypt/decrypt/AES/توقيع رقمي — لم يُعثر على أي نظام تشفير محلي حقيقي لبيانات التخزين المحلي (chrome.storage.local)، ولا لكائن الترخيص المخزَّن، ولا لأي بيانات تقارير محلية. الحماية ليست تشفيرية بل حماية إجرائية/خادمية (server-backed).

9.2 طبقات الحماية الفعلية الموجودة

  1. تحقق الترخيص من الخادم: checkActivationForPremiumFeature(featureName) تقرأ haduri_activation محليًا وتتحقق من: أن الحساب "مفعَّل" (activated)، وأن تاريخ الانتهاء (expiryDate) ما زال ساريًا.
  2. تحقق دوري من الخادم (Periodic Validation): _periodicLicenseValidation يستدعي admin-api بإجراء validate-license: عند فتح أول جلسة يوم جديد، أو كل 4 ساعات، أو عند الإجبار. عند فشل التحقق: يُحذف haduri_activation وhaduri_last_validation* محليًا، تظهر رسالة تنبيه، وتُعاد تحميل الصفحة (إبطال فوري للوصول).
  3. صلاحيات Manifest محدودة: فقط storage وunlimitedStorage، بدون صلاحيات شبكة/تبويبات واسعة، ما يقلل سطح الهجوم على مستوى صلاحيات المتصفح نفسها.
  4. بوابة شروط استخدام إلزامية: haduri_terms_accepted_v900 يجب أن تكون مضبوطة قبل السماح بأي ميزة، مع نافذة شروط إجبارية (showMandatoryTermsModal).
  5. حماية فكرية/قانونية معلَنة: رقم تسجيل ملكية فكرية مذكور صراحة في وصف الإضافة على متجر Chrome (26-12-64959711) كرادع قانوني، وليس آلية تقنية.

9.3 مسار المطوّر الداخلي (Developer Internal Track) — موجود لكنه خامل افتراضيًا

اكتُشف ملف developer/dev_internal_track_resolver.js مضاف فعليًا في manifest.json (أول سكربت في القائمة الثانية)، وهو طبقة "resolver" تسمح — نظريًا فقط — بتجاوز حالة الاشتراك/الوصول للميزات/متطلبات الدفع، لكنها مصمَّمة كبوّابة صريحة ومغلقة افتراضيًا:

const isDeveloperInternalActive = Boolean(
  activationSource &&
  activationSource.isActive === true &&
  activationSource.source === "developer-internal"
);

هذا المسار لا يُفعَّل من أي مكان في content.js الحالي — تم البحث صراحة ولم يُعثر على أي سطر يضبط globalThis.__HADURI_EXTRA_DEV_INTERNAL_TRACK_ACTIVATION__، أي أن المسار الإنتاجي الفعلي (المستخدَم من قِبل المستخدمين النهائيين) لا يتأثر إطلاقًا بوجود هذا الملف، وهو مخصَّص كأداة اختبار داخلية مستقبلية للمطوّر نفسه (بحسب توثيق docs/developer_internal_track_* المرفق في المشروع، والذي يؤكد صراحة أن كل دفعات هذا المسار "لا تغيّر أي سلوك تشغيلي" حتى الآن).

9.4 نقاط ضعف/ملاحظات أمنية موثَّقة

  • الاعتماد الكامل على جلسة الموقع الأصلي للمصادقة يعني أن أي تغيير في آلية التوكن أو أسماء الحقول في الموقع الحكومي قد يكسر الوظيفة، أو (نظريًا) يعرّض بيانات الطلبات الملتقطة (Authorization headers, request bodies) للتخزين المحلي غير المشفَّر لفترة أطول من عمر الطلب نفسه.
  • تخزين حقول دفع مؤقتة (msd_temp_email, msd_temp_phone, msd_temp_manager, msd_temp_org) في localStorage الخاص بصفحة الموقع نفسه (وليس تخزين الإضافة المعزول) هي نقطة حساسة توثيقيًا.
  • لا توجد آلية توقيع أو تحقق تكامل (integrity check) لكائن haduri_activation المخزَّن محليًا سوى التحقق الدوري من الخادم.

10. آلية الاشتراك والتفعيل والدفع

10.1 خطط الاشتراك المكتشفة في الكود

الخطةالمدةالسعر (ريال سعودي)
ربع سنوي (Quarterly)3 أشهر99 ريال
نصف سنوي (Semi-Annual)6 أشهر199 ريال
سنوي (Annual)12 شهرًا390 ريال

(المبالغ داخل الكود بوحدة الهللة: 9900/19900/39000، وهي القيمة الافتراضية amount = 9900 في initMoyasarPayment).

10.2 تدفّق الدفع والتفعيل

  1. المستخدم يختار خطة من showSubscriptionModal().
  2. initMoyasarPayment(amount) يستدعي Supabase Edge Function create-invoice (بمعرّفات: المبلغ، الوصف، البريد، الجوال، الاسم، رابط استدعاء العودة callback_url) وتُستقبل invoiceUrl وinvoiceId.
  3. المستخدم يُكمل الدفع عبر نافذة/بوابة Moyasar (بطاقات، Apple Pay، إلخ حسب ما تدعمه مكتبة moyasar.js).
  4. بعد الدفع، checkPaymentCallback() يقرأ عوامل الرابط (status, id, message) من عنوان URL عند العودة.
  5. عند النجاح، verifyPaymentWithBackend(payment, emailOverride) يستدعي verify-payment الذي يُرجع licenseKey وتفاصيل الخطة وتاريخ الانتهاء.
  6. البيانات تُحفَظ في كائن haduri_activation المحلي (activated, code, email, phone, manager, org, startDate, expiryDate, plan, invoiceId, isRenewal, isEarlyRenewal, daysLeft المشتق).
  7. تُمسح الحقول المؤقتة للدفع من تخزين الصفحة بعد النجاح.

10.3 استرجاع اشتراك سابق (Restore License)

  • restoreLicense() يستدعي check-license بالجوال (Phone) فقط بدايةً، ثم — إن طلب الخادم requireOrg: true — يُطلب من المستخدم أيضًا تأكيد اسم جهة العمل (Organization) كتحقق إضافي قبل الاسترجاع.
  • عند النجاح، _activateFromData(data) تُخزِّن بيانات التفعيل المسترجَعة محليًا وكأنها اشتراك جديد نشط.

10.4 استمرارية التفعيل (Renewal Awareness)

  • الواجهة تحسب daysLeft ديناميكيًا وتعرض حالات "تجديد مبكر" (isEarlyRenewal) و"تجديد" (isRenewal) بألوان حدود مختلفة حسب الخطة المختارة عند التجديد (الحدود الملوّنة تتغيّر حسب السعر 99/199/390).
  • الميزات المدفوعة (Premium) الموثَّقة تشمل: التقارير السنوية، تصدير Excel المتقدم، مخرجات PDF مخصَّصة، تقارير احترافية معينة، وشاشات إدارة الاشتراك/الفاتورة — وكلها تمرّ عبر بوّابة موحّدة checkActivationForPremiumFeature(featureName).

11. فجوات معرفية وأمور غير مؤكدة (لأمانة التوثيق)

  • لا يوجد جدول تعريف رسمي كامل لكل قيم LoginMethod أو لقيم TransactionTypeID الأخرى غير 0/1 (أي 2/3) في الكود الحالي.
  • لا يوجد enum معتمد كامل لكل قيم حقل Status القادم من الواجهة الخلفية للموقع الحكومي.
  • ملفات popup.html/popup.js تحتوي منطقًا موازيًا (تصدير، رسائل) لكنها غير موصولة فعليًا بالمانفست الحالي — تُعامَل كملفات قديمة/احتياطية.
  • لا يوجد تأكيد كامل لعدد/أسماء endpoints الدعم (department, administration, lookup) خارج ما التقطته آلية الاعتراض.

12. الخلاصة

"حضوري اكسترا" إضافة Chrome أحادية الملف التشغيلي تقريبًا (content.js)، تعتمد اعتراض شبكة الصفحة المضيفة لإعادة استخدام جلسة تسجيل الدخول الحكومية، وتبني فوقها طبقة تقارير غنية (يومية، شهرية، سنوية، مساءلة) مع احتساب تأخير/انصراف مبكر مبني على أقدم حضور وأحدث انصراف صالحين مقارنة بأوقات دوام قابلة للتهيئة. الحماية الأساسية هي ترخيص مدفوع يُتحقق منه دوريًا عبر خادم Supabase، وليست تشفيرًا محليًا. التصدير يعتمد أسلوبين مختلفين (HTML-كـ-Excel للتقارير المرئية، وXLSX حقيقي للقوالب البسيطة)، وتوجد بذرة "مسار مطوّر داخلي" موثّقة ومغلقة افتراضيًا لم تُفعَّل بعد في المسار الإنتاجي.
